## 1. Edge Device Ingestion Authentication & Anti-Spoofing

### Context & Challenge
The Ingestion Gateway exposes HTTP (`:8080`) and gRPC (`:50051`) endpoints receiving up to 50,000 readings/sec across thousands of concurrent industrial IoT devices. Without perimeter authentication:
1. Malicious or misconfigured external clients can inject arbitrary or forged telemetry directly into the stream-processing pipeline.
2. A compromised device could submit readings on behalf of other devices (`device_id` spoofing), corrupting partition-local baselines and causing false anomaly alerts.

### Decision
Implement dual authentication mechanisms at the gateway perimeter:
- **Mutual TLS (mTLS)** for devices supporting X.509 client certificates. The gateway configures `tls.Config{ClientAuth: tls.RequireAndVerifyClientCert, ClientCAs: caCertPool}`.
- **Pre-Shared API Keys (Bearer Tokens)** for resource-constrained edge microcontrollers where full TLS client certificate storage/processing is prohibitive. Keys are passed via `Authorization: Bearer <key>` or gRPC metadata `authorization`.
- **Cryptographic Anti-Spoofing Invariant**: The authenticated device identity extracted from the client certificate (Common Name or DNS/URI SAN) or API key claims is strictly validated against the telemetry payload's `reading.device_id`. If `identity != reading.device_id`, the gateway rejects the request with HTTP 403 Forbidden or gRPC `PermissionDenied`.
- **Zero-Lock Hot Path (Constitution Principle I)**: Authenticated credentials (API keys and CA pools) are held in read-only atomic structures (`atomic.Pointer` / read-heavy maps), ensuring authentication verification never blocks or acquires cross-thread locks on the ingestion hot path.

### Alternatives Considered
- **OAuth2 Token Exchange on Edge Devices**: Rejected due to high edge complexity and latency overhead ($>100\text{ms}$ handshake) incompatible with high-frequency $50\text{k}\text{ ev/s}$ streaming.
- **Payload Signature Signing per Record**: Rejected because computing asymmetric RSA/ECDSA signatures on every individual measurement degrades edge throughput by $10\times$–$50\times$. mTLS delegates cryptographic authentication to the transport layer once per TLS session.

## 2. ChronoDB Query API Authentication & Role-Based Access Control (RBAC)

### Context & Challenge
ChronoDB exposes historical telemetry and downsampled rollups over REST (`:8084`) and gRPC (`:50054`). Unrestricted access exposes proprietary telemetry, operational anomalies, and infrastructure device catalogs.

### Decision
- **Bearer JWT Authentication**: Queries require standard JSON Web Tokens (JWT) signed with HMAC-SHA256 (`HS256`) or Ed25519/RSA.
- **Fine-Grained RBAC Roles**:
  - `Viewer`: Read access to historical raw time series (`/api/v1/query`) and device catalog (`/api/v1/devices`).
  - `Operator`: Read access + operational rollups (`/api/v1/query/rollup`) + health metrics.
  - `Admin`: Full access including compaction triggers and administrative configurations.
- **Tenant & Device Scope Isolation**: Token claims support `allowed_devices: ["turbine-alpha-*"]` glob patterns. Query requests specifying `device_id` outside the token's allowed scopes are rejected with HTTP 403 Forbidden.
- **Zero External Dependency Implementation**: Pure Go implementation using standard library `crypto/hmac`, `crypto/sha256`, and `encoding/base64`, maintaining static binary compilation (`CGO_ENABLED=0`) and minimizing supply-chain vulnerability attack vectors.

### Alternatives Considered
- **External Identity Provider (OIDC/Keycloak) Sidecar**: Evaluated, but creates a hard runtime dependency for standalone or air-gapped deployments. The chosen JWT validator supports standard signed tokens from any external IdP while operating independently.

## 3. Webhook Integrity & Replay Attack Defense (HMAC-SHA256)

### Context & Challenge
The decoupled alert dispatcher (`alertd`) pushes incident notifications to external webhook endpoints (e.g. PagerDuty, Slack, custom webhook gateways). Receivers need cryptographic assurance that alerts were genuinely generated by Pulse and have not been tampered with or replayed.

### Decision
- **Payload Signing**: `alertd` computes `HMAC-SHA256(secret, timestamp + "." + body)` over the exact serialized JSON payload and an epoch timestamp.
- **HTTP Headers**:
  - `X-Pulse-Signature: sha256=<hex_digest>`
  - `X-Pulse-Timestamp: <unix_epoch_seconds>`
- **Replay Protection**: The receiver checks that $|T_{\text{current}} - T_{\text{header}}| \le 300\text{ seconds}$ (5 minutes drift tolerance). Requests older than 300 seconds are discarded.
- **Constant-Time Verification**: Verification uses `crypto/subtle.ConstantTimeCompare` to defend against timing side-channel attacks.

### Alternatives Considered
- **Mutual TLS to Webhook Sinks**: Often unsupported by commercial webhook receivers (e.g., Slack, Discord). HMAC headers are the industry standard (GitHub, Stripe, Twilio) for webhook authenticity.

## 4. Hot-Path Ingestion Rate Limiting

### Context & Challenge
A compromised or malfunctioning IoT device could flood the Ingestion Gateway with millions of requests, causing denial of service (DoS) for legitimate sensors.

### Decision
- **Per-Device / Per-IP Token Bucket Limiter**: In-memory token bucket rate limiter storing atomic counters or sharded token buckets.
- **Zero Lock Contention**: Partitioned or atomic decrement operations ensure that checking rate limits incurs $< 0.05\text{ms}$ latency overhead.
- **HTTP 429 & Retry-After**: Excess traffic is dropped at the HTTP/gRPC boundary with status 429 Too Many Requests and an optional `Retry-After: 1` header before touching Redpanda.

## 5. Kubernetes NetworkPolicies & Secret Management

### Context & Challenge
Kubernetes flat networks allow any pod to reach any other pod by default. If an edge gateway or simulator pod is compromised, an attacker could attempt to directly query the database or connect to Redpanda.

### Decision
- **Default-Deny Ingress**: All service namespaces enforce default-deny ingress policies.
- **Explicit Least-Privilege Rules**:
  - `gateway`: Ingress on 8080/50051 from external traffic; egress only to Redpanda broker (9092) and DNS.
  - `processor`: Ingress on 8081 (/healthz, /metrics); egress only to Redpanda broker (9092) and DNS.
  - `alertd`: Ingress on 8083 (/healthz, /metrics); egress to Redpanda (9092) and external webhook destinations.
  - `chronod`: Ingress on 8084/50054 from authorized query clients; egress only to Redpanda (9092) and DNS.
- **Secret Management**: Certificates, private keys, HMAC secrets, and JWT keys are stored as Kubernetes `Secret` resources and mounted as read-only volumes (`mode: 0400`) into `/etc/pulse/secrets/`. Containers run as non-root `UID 65532` (`readOnlyRootFilesystem: true`, `drop: ["ALL"]`).
